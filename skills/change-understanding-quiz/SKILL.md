# 変更理解クイズ

PRを出す開発者に、今回の実装の挙動とコードの処理を自分の言葉で説明してもらう。実装を含むPRは、ドラフトを含めて全問正解後に作成する。

## 1. 出題対象を確定する

- PRの比較先と `origin` が作成先と同じリポジトリであることを確認する。GitHubの確認には `gh` を優先する。forkから別のリポジトリへのPRはこのフックの対象外と説明し、合格扱いにしない。
- コミットやpushの権限は既存の指示に従う。未コミットの変更があれば、まず必要な承認を得てコミット対象を確定する。クイズの都合で勝手にコミットしない。
- 比較先の情報を取得し、次を実行する。`<skill-dir>` はこのファイルのあるディレクトリの絶対パス、`<base>` は `main` などGitHub上の比較先ブランチ名。`origin/<base>` があればそれを優先し、なければローカルの `<base>` を参照する。

```sh
sh <skill-dir>/scripts/run.sh snapshot --base <base>
```

ランチャーはCodex desktopが提供する `CODEX_MCP_NODE_PATH` の同梱Node.jsを使う。参照できない環境ではその旨を伝え、ランタイムを勝手にインストールしない。

出力JSONの `implementation_paths` が空なら、クイズと合格記録を省略し、依頼されたPR作成に進む。実装差分がある場合は、出力JSONを出題時の `snapshot` として保持する。比較先との実装差分と関連するコードを読み、文書の変更は出題範囲から除く。

## 2. 実装理解のクイズ

出題前に、差分ビューアを操作できる場合は開き、PRの比較先に対するブランチ差分を表示する。ビューアを開けない場合や同じ差分を表示できない場合は、対象ファイルへの参照と、問題に必要な実装差分の抜粋を会話に示す。

通常は3問を目安にする。小さな変更なら2問に絞り、独立した重要な変更が複数あれば増やす。次の2区分を少なくとも1問ずつ含め、問題ごとに別の挙動や処理を扱う。採点基準は実装を読んで定める。

- **挙動（spec）**。変更後に具体的な入力や操作を与えると、何が返るか、何が変わるか。
- **処理（technical）**。変更したコードがどの条件でどの処理を通り、結果や状態をどう変えるか。

各問に、対象のファイルや関数、何が変わったかを示す短い説明、回答に必要な入力・設定・初期状態、答えてほしい結果や処理を含める。差分ビューアを見ていても、別の問題や会話中の説明から前提を推測させない。前提を説明する際は、問う結果や分岐の答えを先に明かさない。

たとえば「期限切れならどうなりますか？」とだけ聞く代わりに、「`src/cache.ts` の `getOrLoad` でキャッシュの期限判定を変更しました。キーには値が保存されていて、現在時刻と有効期限が等しいとします。この呼び出しは保存済みの値を返しますか、それともローダーを呼びますか。どの条件式でそう決まるかも説明してください」と聞く。

実装した開発者が、自分の言葉で説明できる問題にする。事前の予想、検証の限界、不確実性、出荷判断は出題しない。行番号や識別子の暗記も問わない。コードを参照して回答してよい。初回は模範解答を示さない。

出題後は本人の返答を待つ。回答用ツールが使えない場合は、会話で出題してターンを終える。自分やサブエージェントで本人の回答を代筆しない。

## 3. 採点と再出題

- 各回答について正誤、採点理由、根拠を示す。表現が異なっても意味が正しければ正解にする。情報不足は短く聞き直す。
- 誤答には誤解を説明し、同じ概念を別の入力や状況で問い直す。解説の復唱だけで合格にしない。正解済みの論点は保持できる。
- 実装や要件の問題が見つかったら作業へ戻る。出題中にHEAD、ブランチ、比較先やコードが変わったらsnapshotを更新して出題し直す。文脈を失ったら履歴を確認し、確認できない回答を正解扱いにしない。
- 全問について本人の理解を確認できるまで繰り返す。連敗回数を理由に合格にしない。中断の希望には従い、PRを作成しない。

## 4. 合格の記録とPR作成

全問正解後に、作業ツリーの外の一時ファイルへ以下のJSONを作る。本人の回答を忠実に記録する。再出題した問は最終的に正解した問題と回答を使う。

```json
{
  "version": 3,
  "snapshot": {"出題時のsnapshot出力をそのまま入れる": "この例を実データに置き換える"},
  "questions": [
    {"category": "spec", "question": "実際の問題", "answer": "本人の回答", "correct": true, "reason": "採点理由と根拠"},
    {"category": "technical", "question": "実際の問題", "answer": "本人の回答", "correct": true, "reason": "採点理由と根拠"}
  ]
}
```

```sh
sh <skill-dir>/scripts/run.sh pass --base <base> --record <回答記録.json>
sh <skill-dir>/scripts/run.sh check --base <base>
```

合格記録は対象worktreeのGit管理ディレクトリに保存する。スクリプトは記録の形式と対象コミットを検査し、回答の意味の採点はCodexが担当する。旧形式の記録は再受験にする。

PR作成が依頼済みなら、既存の承認要件を満たしてから `gh pr create --base <base> ...` を単独コマンドで実行する。リポジトリはツールの作業ディレクトリで指定し、`--repo` と `--head` は使わない。合格だけをpushやPR作成への許可とみなさない。テンプレートに従い、クイズの回答をPR本文へ勝手に掲載しない。

スキル単体では会話上の制約になる。配布元のフックを別途有効にすると、通常のPR作成コマンドで合格を確認できる。フックは学習用であり、動的なコマンドやブラウザ操作を網羅するものではない。フックを迂回するために別のツールやコマンド表現へ切り替えない。
