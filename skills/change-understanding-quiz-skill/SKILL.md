# 変更理解クイズ

PRを作る前に、利用者が今回の変更の挙動と実装理由を説明できるか確認する。GitやPRの一般知識を問う試験にはしない。出題と採点は会話で行い、全問正解までPR作成を保留する。ドラフトPRも同じ扱いにする。

## 1. 出題対象を確定する

- 利用者の要件、リポジトリの指示、PRテンプレート、差分、変更箇所の呼び出し元、関連する実装とテストを読む。差分だけから仕様を推測しない。
- PRの比較先を確認する。GitHubの確認には `gh` を優先する。`origin` とPRの作成先が同じリポジトリであることを確認する。forkから別のリポジトリへのPRはこのフックの対象外と説明し、合格扱いにしない。
- コミットやpushの権限は既存の指示に従う。未コミットの変更があれば、まず必要な承認を得てコミット対象を確定する。クイズの都合で勝手にコミットしない。
- 比較先の情報を取得してから、次を実行する。`<skill-dir>` はこの `SKILL.md` があるディレクトリの絶対パスに置き換える。`<base>` は `main` など、GitHub上の比較先ブランチ名。`origin/<base>` があればそれを優先し、なければローカルの `<base>` を参照する。

```sh
python3 <skill-dir>/scripts/gate.py snapshot --base <base>
```

出力のJSONを出題時の `snapshot` として保持する。`git diff <merge_base>..HEAD` と関連ファイルを読み、対象範囲を利用者に短く示す。差分がなければ比較先を見直す。実装と要件が矛盾していたら先に解決し、バグを正解として教えない。

## 2. 本人に出題する

通常は3〜5問とし、変更の大きさに応じて増減する。仕様と技術を少なくとも1問ずつ含める。各問の採点基準と根拠ファイルを出題前に定める。

- **仕様（spec）**: 具体的な入力や利用者操作に対する結果、従来との違い、失敗時の挙動。
- **技術（technical）**: 実際の処理経路、実装を選んだ理由、境界条件、その変更を確かめた操作やテストの意味。

本人の言葉で説明する形式にする。些末な行番号や識別子の暗記は問わない。問題文で答えを教えず、初回は模範解答を見せない。必要ならコードの参照は認める。

出題したら本人の返答を待つ。回答用ツールが使えない場合は、会話の返答として出題してターンを終える。自分やサブエージェントで利用者の回答を代筆しない。

## 3. 採点と再出題

- 各回答について正誤、採点理由、根拠箇所を示す。表現が異なっても意味が正しければ正解にする。情報不足は短く聞き直す。
- 誤答には誤解している点を説明し、同じ概念を別の入力や状況で問い直す。解説の復唱だけで合格にしない。正解済みの論点は保持できる。
- 全問について本人の回答を確認できるまで繰り返す。連敗回数を理由に合格にしない。利用者が中断した場合は中断し、PRを作成しない。
- 出題中にHEAD、ブランチ、比較先やコードが変わったらsnapshotを更新して出題し直す。文脈を失ったときは回答履歴を確認し、確認できない回答を正解扱いにしない。

## 4. 合格を記録し、PR作成へ進む

全問正解後に、作業ツリーの外の一時ファイルへ以下のJSONを作る。回答は本人の返答を忠実に記録する。再出題した問は最終的に正解した問題と回答を使う。

```json
{
  "snapshot": {"出題時のsnapshot出力をそのまま入れる": "この例を実データに置き換える"},
  "questions": [
    {"category": "spec", "question": "実際の問題", "answer": "本人の回答", "correct": true, "reason": "採点理由と根拠ファイル"},
    {"category": "technical", "question": "実際の問題", "answer": "本人の回答", "correct": true, "reason": "採点理由と根拠ファイル"}
  ]
}
```

```sh
python3 <skill-dir>/scripts/gate.py pass --base <base> --record <回答記録.json>
python3 <skill-dir>/scripts/gate.py check --base <base>
```

合格記録は対象worktreeのGit管理ディレクトリに保存される。スクリプトは記録の形式と対象コミットを検査する。回答の意味の採点はこのスキルを使うCodexが担当する。

PR作成が依頼済みなら、既存の承認要件を満たしてから `gh pr create --base <base> ...` を単独コマンドで実行する。リポジトリはツールの作業ディレクトリで指定し、`--repo` と `--head` は使わない。クイズへの合格だけをpushやPR作成への許可とみなさない。テンプレートに従い、クイズの回答をPR本文へ勝手に掲載しない。

スキルだけでは会話上の制約になる。配布元のフックを別途有効にすると、通常のPR作成コマンドで合格を確認できる。フックは学習用であり、動的なコマンドやブラウザ操作を網羅するものではない。フックを迂回するために別のツールやコマンド表現へ切り替えない。
